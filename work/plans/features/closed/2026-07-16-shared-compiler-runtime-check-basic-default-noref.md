## Summary

Before this change, L0 Stage 2 and L1 Stage 1 native compiler binaries used the full checked L0 runtime with only the
compiler-specific `_RT_QUARANTINE_MAX_COUNT=256` setting. Reducing quarantine retention alone did not remove the
dominant interior-pointer tracking cost introduced by full runtime pointer validation.

The assessment recorded in
[work/plans/features/attachments/2026-07-15-l0-l1-compiler-performance-assessment.md](../attachments/2026-07-15-l0-l1-compiler-performance-assessment.md)
found that explicitly building the assessment-snapshot compilers with basic checks reduced compiler-only `--gen` wall
time by approximately 16 to 18 percent for L0 and 21 to 25 percent for L1 across the fixed hello, hamurabi, and hashmap
workloads. Full and basic compiler binaries at the same snapshot generated byte-identical C, so the difference was
isolated to the compiler executable's own runtime mode. The attachment is the authoritative record of methodology,
complete statistics, confidence intervals, and historical localization; this plan retains only the decision-driving
summary.

This work makes basic checked validation plus the existing 256-record quarantine cap the default for native compiler
binaries. It also gives L1 a complete, level-named Make interface for choosing the runtime mode and quarantine settings
of its L0-hosted Stage 1 compiler. Programs produced by those compilers and the prebuilt L1 runtime archives remain full
checked by default.

## Pre-implementation State

1. L0 defaults `L0_COMPILER_RT_QUARANTINE_MAX_COUNT` to `256`. Its compiler-build helper adds only the corresponding
   quarantine define unless callers opt into basic or unchecked mode through existing L0 build flags.
2. L0 developer, install-prefix, distribution, and triple-bootstrap workflows share this compiler-only quarantine
   policy, but the triple-bootstrap test also carries a parallel flag-composition implementation.
3. L1 defaults `L1_COMPILER_RT_QUARANTINE_MAX_COUNT` to `256`. Its Stage 1 build helper adds that L0 runtime define to
   `L0_CFLAGS` because the L1 compiler is an L0 executable.
4. L1 has no level-named compiler-runtime mode or quarantine-byte controls. Building a basic or unchecked L1 compiler
   currently requires callers to know and inject the underlying L0 runtime defines through `L0_CFLAGS`.
5. L1 runtime archives are intentionally different from the compiler executable: `make -C l1 runtime` builds full,
   traced, unchecked, and check-basic variants together, while `L1_RT_QUARANTINE_MAX_*` tunes those archives.

## Defaults and Public Make Interface

The implementation exposes this compiler-build surface:

| Purpose                             | L0                                        | L1                                             |
| ----------------------------------- | ----------------------------------------- | ---------------------------------------------- |
| Default basic compiler runtime      | `L0_COMPILER_RT_CHECK_BASIC ?= 1`         | `L1_COMPILER_RT_CHECK_BASIC ?= 1`              |
| Explicit unchecked compiler runtime | Existing `L0_RT_UNCHECKED=1`              | `L1_COMPILER_RT_UNCHECKED=1`                   |
| Compiler quarantine byte limit      | Existing `L0_RT_QUARANTINE_MAX_BYTES=<n>` | `L1_COMPILER_RT_QUARANTINE_MAX_BYTES=<n>`      |
| Compiler quarantine record limit    | `L0_COMPILER_RT_QUARANTINE_MAX_COUNT=256` | `L1_COMPILER_RT_QUARANTINE_MAX_COUNT=256`      |
| Raw compiler-build C options        | `L0_CFLAGS`                               | `L0_CFLAGS`, because Stage 1 is compiled as L0 |
| Generated-program C options         | `L0_CFLAGS`                               | Existing `L1_CFLAGS`                           |

The default compiler flags are `-DL0_RT_CHECK_BASIC -D_RT_QUARANTINE_MAX_COUNT=256`. Quarantine bytes retain the
runtime's existing default unless explicitly overridden.

Mode selection follows this precedence:

1. An explicit `-DL0_RT_CHECK_BASIC` or `-DL0_RT_UNCHECKED` form already present in `L0_CFLAGS` wins. The build helper
   preserves it without adding or duplicating another mode define.
2. For L1, a nonempty `L1_COMPILER_RT_UNCHECKED` selects unchecked mode and suppresses the default basic define.
3. Otherwise, a nonempty compiler-specific check-basic variable adds `-DL0_RT_CHECK_BASIC`.
4. Explicitly empty check-basic and unchecked variables select the full checked compiler runtime.

Quarantine selection is independent from mode selection:

1. An explicit `_RT_QUARANTINE_MAX_BYTES` or `_RT_QUARANTINE_MAX_COUNT` define already present in `L0_CFLAGS` wins for
   that limit.
2. L0 preserves the existing explicit `L0_RT_QUARANTINE_MAX_*` precedence over compiler defaults.
3. L1 uses `L1_COMPILER_RT_QUARANTINE_MAX_*` only for the compiler executable. These variables do not alter
   `L1_RT_QUARANTINE_MAX_*` or any L1 runtime archive.
4. An explicitly empty compiler quarantine variable disables only that compiler-specific default. It does not disable
   the selected runtime mode or the other quarantine limit.

## Implementation

### Phase 1: Centralize L0 compiler-build defaults

1. Add `L0_COMPILER_RT_CHECK_BASIC ?= 1` to the L0 Make interface and pass it through every compiler-producing target.
2. Extend the L0 compiler-build environment helper to compose mode and quarantine flags independently. Remove the
   current behavior where an explicit quarantine count can return early and suppress later mode handling.
3. Keep direct script invocation, developer artifacts, install-prefix builds, distribution bootstrap/self-host builds,
   and the triple-bootstrap chain on the same default and override contract.
4. Update the triple-bootstrap flag helper to use the same precedence and require all three compiler stages to receive
   equivalent runtime-mode and quarantine flags.

### Phase 2: Add meaningful L1 Make parity

1. Add `L1_COMPILER_RT_CHECK_BASIC ?= 1`, `L1_COMPILER_RT_UNCHECKED`, and `L1_COMPILER_RT_QUARANTINE_MAX_BYTES`
   alongside the existing compiler quarantine-count variable.
2. Pass all compiler-specific variables from `build-stage1` to `build_stage1_l1c.py` and translate them to the L0
   runtime defines used to compile `l1c-stage1.native`.
3. Preserve explicit `L0_CFLAGS` as the raw escape hatch for the L0 compilation step, while documenting that `L1_CFLAGS`
   controls C compilation performed later by the built L1 compiler.
4. Reorganize `make -C l1 help` so compiler construction, generated-program, runtime-archive, and test controls are
   distinct. List each variable once and remove the existing duplicate trace-variable entries.
5. Do not add `L1_RT_CHECK_BASIC` or `L1_RT_UNCHECKED`. The L1 runtime already produces separate archives for those
   modes, and the L1 driver selects them through `--check-basic` or `--unchecked`.

### Phase 3: Preserve generated-program and archive defaults

1. Verify that a default-built compiler invoked without `--check-basic` emits no basic-mode prelude define.
2. Keep the default L1 archive as the full checked archive and continue building the separate check-basic, unchecked,
   and traced archives.
3. Keep L0 Stage 1 Python outside the native compiler-runtime policy because it does not embed the L0 C runtime.
4. Update the shared ADR and both level design-decision documents to state that delivered/developer native compiler
   binaries use basic checks plus the compiler-only quarantine cap, while generated user programs remain full checked by
   default.

## Non-Goals

- No change to `l0c` or `l1c` CLI modes, generated-C mode selection, exit codes, or diagnostics.
- No change to the full checked default for generated user programs or the default L1 runtime archive.
- No new runtime mode, archive variant, runtime API, compiler diagnostic code, or language type.
- No L1 install, distribution, release, Stage 2, or triple-bootstrap target work. The active L1 Stage 2 plan can reuse
  this compiler-runtime interface when that stage is implemented.
- No permanent compiler performance harness in the repository as part of this work.

## Verification Criteria

### Build-flag and interface tests

1. Table-driven L0 and L1 helper tests cover default basic plus q256, explicit full mode, explicit basic and unchecked
   flags, explicit quarantine bytes/count, empty quarantine defaults, deduplication, and input-environment immutability.
2. An explicit quarantine define does not suppress the default basic mode, and disabling q256 does not disable basic
   mode.
3. L1 compiler-only variables do not change L1 runtime archive configuration stamps or archive hashes.
4. `make -C l1 help` lists the supported compiler-build and generated-program variables once with their distinct
   meanings.

### Workflow and semantic isolation

1. `make -C l0 test-dist` shows basic plus q256 in the effective compiler-build flags while programs built by the
   distributed compiler retain the normal full checked default.
2. `make -C l0 triple-test` builds all self-hosted compiler stages with equivalent default flags and retains its native
   and generated-C identity guarantees.
3. Isolated default, explicit-full, and explicit-unchecked L1 Stage 1 compiler builds complete and compile their
   assigned examples successfully.
4. Default and explicit-basic compiler builds generate byte-identical C for fixed L0 and L1 inputs.
5. Plain `--gen` output contains no `L0_RT_CHECK_BASIC` or `DEA_RT_CHECK_BASIC` define unless the caller explicitly
   passes `--check-basic`.

### Performance evidence and full validation

1. Re-run the warm-cache compiler assessment with two warmups and 30 measured randomized-block runs for `--gen` and
   `--build`. Treat timings as non-gating evidence; the default build should statistically match the explicit-basic
   build and retain a clear compiler-only advantage over explicit full mode. Append the dated implementation
   confirmation to
   [work/plans/features/attachments/2026-07-15-l0-l1-compiler-performance-assessment.md](../attachments/2026-07-15-l0-l1-compiler-performance-assessment.md).
2. Run `make -C l0 test-all`.
3. Run `make -C l0 test-dist`.
4. Run `make -C l0 triple-test`.
5. Run `make -C l1 test-all`.
