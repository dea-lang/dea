# L1 Initiative 0003 - C FFI / C Interoperability

- Version: 2026-04-25
- Status: Active
- Kind: Initiative

## Summary

This initiative adds full C foreign-function interface support to L1: `extern "C"` declaration blocks for declaring
C-callable surfaces, a closed FFI-safe type set enforced by the analyzer, and `cstr` as the distinct null-terminated
string boundary type. Today's FFI is a single primitive (`extern func` with no name mangling); this initiative replaces
that with a typed, mangling-aware boundary so L1 programs can bind C libraries directly.

This initiative executes under the L1 roadmap ([`l1/docs/roadmap.md`](../../docs/roadmap.md)).

## Related initiatives

- **Initiative 0001 - Separate Compilation and External Linking**
  ([`0001-separate-compilation-and-linking.md`](0001-separate-compilation-and-linking.md)) is a hard prerequisite. C FFI
  builds on the LBI mangling, the separate-compilation driver surface, and the external-library linking CLI defined
  there. Read 0001 first.
- **Initiative 0002 - L1 Runtime Library** ([`0002-runtime-static-library.md`](0002-runtime-static-library.md)) is a
  soft prerequisite. The runtime split is not strictly required for the FFI surface, but it shapes the link model this
  initiative consumes. The `dea_siphash.h` aside in 0002 also points to a possible future tranche where SipHash is
  exposed through this FFI surface as a dedicated shared object.

## Non-goals

- **Automatic bindgen-style C-header parsing.** Manual `extern "C"` binding files remain the supported workflow. A
  `bindgen` analogue is something an L1 program can build later; it does not need to ship with the compiler.
- **New calling conventions.** L1 emits and consumes only the platform default C calling convention (`cdecl` on x86-32,
  System V AMD64 on x86-64 POSIX, AAPCS on ARM, MS x64 on Windows). No `stdcall`, `vectorcall`, or similar.
- **Backporting to L0.** L0 stays with its existing `extern func` primitive. Everything in this initiative lands in
  `l1/`.
- **Dynamic loading at runtime.** No `dlopen`/`LoadLibrary` shim. Dynamic linking here means classic load-time linking
  against a `.so`/`.dylib`/`.dll` through the linking CLI defined in 0001.

## Current baseline

Relevant FFI-only facts that constrain the plan:

- `extern func` is the only FFI primitive today. Extern symbols are intentionally **not name-mangled** at the C
  boundary; everything else currently uses `dea_{module}_{name}`-style mangling. Initiative 0001 moves L1 to the LBI
  length-prefixed scheme, and `extern "C"` declarations defined here will continue to bypass it.
- L1 has no `extern "C"` block surface, no `cstr` type distinct from `string`, no `extern struct` / `extern enum` /
  opaque-`type` declarations, and no closed FFI-safe type rule enforced by the analyzer.
- Dea `string` values already carry a trailing `\0` byte by construction, and runtime helpers
  (`sys.rt::rt_string_bytes_ptr`, the C-only `_rt_string_bytes`) already expose the underlying byte pointer, but there
  is no typed `string -> cstr` conversion surface that uses them.
- Integral and floating-point scalar types are already implemented in L1's surface and runtime; the FFI work below
  treats them as fully available.
- `compiler/stage1_l0/` is the only implemented L1 compiler today; every change lands first in Stage 1.

## Phase 0 - Anchor decisions before coding

### 0.4 Boundary between L1 types and C types

The cornerstone for this initiative. Decide which L1 constructs cross the FFI boundary unwrapped versus through a
wrapper, and codify a closed set of "FFI-safe" types:

- Integral and floating-point scalars cross unwrapped (already true today).
- `bool` crosses as the underlying C `_Bool` (or `dea_bool`).
- `cstr` is a builtin FFI boundary type distinct from `string`. It is bit-compatible with `byte*` but is a distinct
  surface type with its own typing rules: conversion between `cstr` and `byte*` requires an explicit cast in either
  direction, with no implicit assignment or call-site compatibility. The trailing-null guarantee is therefore a
  type-level fact, not just documentation, even though the representations are identical.
- Dea strings already carry a trailing `\0` byte by construction, so crossing a `string` into a `cstr` is a zero-cost
  reinterpretation of the string's byte pointer, not a copy. The supporting runtime primitives already exist
  (`sys.rt::rt_string_bytes_ptr`, or the C-only `_rt_string_bytes`); the conversion surface is a thin boundary-level
  reinterpretation over those helpers, not a new `std.string` function. `std.string` is a user-facing module and is not
  the right home for a runtime-lowering helper.
- `string` **never** crosses unwrapped; it carries ARC and length metadata, and the C boundary only sees the raw byte
  pointer through the `cstr` reinterpretation.
- Pointers (`T*`, `T*?`) cross as raw C pointers; ownership annotations are L1-side only.
- Owned `struct`/`enum` types do not cross; only `extern struct`/`extern enum` do.
- L1 `T?` over non-pointer `T` does not cross; the wrapper struct is L1-only.

Anything outside this set produces a dedicated diagnostic at the FFI boundary.

## Phase 4 - Full C FFI

Phase number kept as `4` to align with the original four-phase ordering in Initiative 0001 and the spawned-plan Summary
text. The only phase here that meaningfully extends the type system. To bind C usefully we need extern types, extern
globals, and a closed set of FFI-safe types enforced by the analyzer.

### 4a. Extern declarations

Add `extern "C"` blocks as the C-linkage envelope for FFI declarations. Inside the block, L1 supports:

- `func` declarations for C-callable functions.
- `struct C_Foo { ... }` for declared C layouts with no L1 ownership and no `new`/`drop`.
- `struct C_Foo;` for opaque structs usable only behind a pointer.
- `type CFile;` for opaque named C types whose internals never matter to L1.
- `enum C_Mode { ... }` for C enum bindings lowered as an integer with named constants. The underlying integral type is
  configurable (`enum C_Mode : int32 { ... }`).
- `let errno: int;` for extern globals.

Every declaration inside an `extern "C"` block is emitted without mangling. The module export manifest from
[Initiative 0001 Phase 0.1](0001-separate-compilation-and-linking.md) still decides whether an FFI declaration is
re-exported to other L1 modules or stays module-private.

C variadic FFI remains part of this initiative and will either land with the main FFI plan or as a sibling tranche under
this initiative. The standalone feature plan
[`l1/work/plans/features/2026-04-22-variadic-functions-noref.md`](../plans/features/2026-04-22-variadic-functions-noref.md)
is limited to L1-defined variadic functions and does not settle `extern func` variadic semantics.

### 4b. FFI-safe type rules

Enforced in the analyzer with dedicated diagnostics. A type is FFI-safe iff it is one of:

- a builtin scalar (the full integral and floating-point set, `bool`, `byte`);
- a raw pointer `T*` or `T*?` where `T` is itself FFI-safe or an opaque extern type;
- an `extern struct` (by value or pointer);
- an `extern enum` (lowered as its underlying integer);
- a `cstr` for null-terminated C strings.

Anything else, including L1 `string`, owned `struct`/`enum`, `T?` over non-pointer `T`, and function types without an
explicit C ABI marker, is rejected at the FFI boundary.

### 4c. Header binding strategy

Two viable options, neither of which moves the compiler surface:

1. **Manual binding files.** The user writes `.l1` modules with `extern "C"` declarations matching a C header. Simple,
   robust, no toolchain dependencies. **Recommended for L1**; it is the only option that ships with the compiler.
2. **`bindgen`-style auto-generation.** A separate tool reads C headers and emits L1 binding modules. **Out of scope.**
   An L1 program can do this once L1 is solid; it doesn't need to be in the compiler.

### 4d. Lifetime and ownership at the boundary

`extern struct` instances are not ARC-managed and have no L1 destructor. The rule: ownership of pointers crossing the
FFI is documented per declaration; L1 makes no claims and runs no cleanup. Idiomatic L1 wrappers (`with`/`cleanup`) over
raw FFI calls remain the standard pattern, exactly as `sys.rt` is wrapped by `std.fs`/`std.io` today.

### 4e. Calling convention

Default and only convention is the platform's C convention. No surface-level convention markers in L1.

### 4f. Diagnostic surface

FFI diagnostics should reuse existing families when the failure is really parse, signature, type, driver, or build
behavior. A new `FFI-*` family remains a candidate if the FFI boundary accumulates enough cross-cutting rules that
mapping them to `SIG-*` / `TYP-*` would obscure the user-facing meaning. Concrete `FFI-*` codes should not be registered
until an implementation change introduces them.

## Sequencing and dependencies

This is a single-phase initiative. It depends hard on Initiative 0001 having landed the LBI mangling, the
separate-compilation driver surface, and the external-library linking CLI. Initiative 0002 is a soft prerequisite that
shapes the link model.

Recorded near-term tranche checkpoint:

- [ ] Phase 4: `cstr` plus `extern "C"` support.

## Cross-cutting concerns

### Stage 1 oracle and future Stage 2 parity

Every change lands in `compiler/stage1_l0/` while L1 is Stage 1-only. `stage1_l0` remains the behavioral oracle. When
`compiler/stage2_l1/` is implemented, this initiative must preserve a Stage 1/Stage 2 parity contract for the equivalent
surface.

### Determinism

Generated C for `extern "C"` declarations and `cstr` lowering must be byte-deterministic so Stage 1 tests can assert
stable output and future L1 triple-bootstrap can work at finer granularity.

### Documentation

Phase 4 lands with corresponding doc updates in the same change:

- Update to [`l1/docs/reference/design-decisions.md`](../../docs/reference/design-decisions.md) capturing the FFI
  policy.
- New [`l1/docs/user/c-ffi.md`](../../docs/user/c-ffi.md) describing the manual-binding workflow and the FFI-safe
  boundary.
- Updates to [`l1/docs/reference/grammar.md`](../../docs/reference/grammar.md) for the `extern "C"` block grammar.

### L0 isolation

L0 is unaffected. The FFI surface lands in `l1/`; L0 retains its existing `extern func` primitive per the `1.0.0` scope
boundary.

## Open questions

These remain open after the decisions above and should be resolved in the phase plan:

1. **`extern "C"` detail surface.** Do FFI declarations need an explicit per-symbol link-name override in addition to
   block-level C linkage, or is the block surface sufficient?
2. **Diagnostic family split.** Keep FFI diagnostics in existing families, or introduce concrete `FFI-*` codes once
   implementation pressure proves a separate family is clearer?
3. **C variadic FFI scope.** Land it with the main `extern "C"` tranche, or carve it out as a sibling tranche under this
   initiative?

Each open question gets a short design note under [`l1/docs/specs/compiler/`](../../docs/specs/compiler/) once decided.

## Glossary

- **FFI-safe type**: the closed set of types permitted across an `extern "C"` boundary (Section 4b).
- **Opaque type**: an extern type whose layout is unknown to L1; usable only behind a pointer.
- **`cstr`**: builtin null-terminated C-string boundary type, bit-compatible with `byte*` but a distinct surface type
  for typing-rule purposes.
