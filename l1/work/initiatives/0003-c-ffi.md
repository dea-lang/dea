# L1 Initiative 0003 - C Interoperability Direction

- Version: 2026-08-30
- Status: On Hold
- Kind: Initiative
- Open plans: (none)
- Closed plans:
  - `l1/work/plans/features/closed/2026-04-24-c-ffi-extern-c-and-cstr-noref.md` (withdrawn pending an initiative-level
    decision)

## Summary

This initiative records the design space for broader C interoperability in L1. It does not currently select or schedule
one first-class C FFI design.

L1 already has an external-call boundary: unmangled `extern func` and `unsafe extern func` declarations call symbols
that use Dea's generated C ABI. That boundary is sufficient for the current runtime and standard library, and it is
sufficient for manual third-party bindings when a small C shim translates between the target library's C ABI and the Dea
ABI.

Three broader designs have been considered:

1. direct typed C declarations through `extern "C"` blocks, extern C layouts, and a builtin `cstr` type;
2. ordinary Dea declarations augmented with C carrier and boundary annotations such as `@c_int`, `@c_size_t`, `@const`,
   and lifetime or string-shape annotations;
3. a separate `dea-cbind` tool that reads selected C declarations and generates a Dea binding module plus a C shim, with
   a mechanical raw layer and optional curated wrappers or corrections.

Each design can work, but each commits Dea to a different split of responsibility between the language, compiler,
runtime, build driver, and external tooling. Current programs do not yet provide enough evidence to justify that
commitment. Initiative 0003 is therefore on hold until real bindings expose repeated problems that the present manual
shim workflow cannot solve cleanly.

This initiative executes under the [L1 roadmap].

## Current decision

The current decision is deliberately narrow:

- do not add new L1 C-FFI syntax or C-specific builtin types now;
- do not implement the draft `extern "C"` plus `cstr` plan now;
- keep existing `extern func` semantics unchanged;
- use pure L1 code or owned runtime helpers for standard-library growth;
- use handwritten Dea-ABI C shims for third-party libraries when direct ABI identity is not proven;
- use [Initiative 0001]'s completed linking surface to supply foreign objects, external library names, search paths,
  runtime search paths, and raw linker arguments;
- reconsider this initiative only after real user programs establish specific, repeated needs.

The initiative is on hold, not rejected. Any of the alternatives below may be resumed, combined, or replaced after that
experience exists.

## What Dea has today

### Existing external-call surface

The implemented syntax is:

```dea
extern func name(args...) -> T;
unsafe extern func name(args...) -> T;
```

These declarations have no Dea body and keep their declared symbol spelling instead of receiving an LBI-mangled source
symbol. Their parameter and result types nevertheless use Dea's generated C representations. An `extern func` is
therefore an external Dea-ABI declaration, not a general promise that any similarly spelled C declaration has the same
ABI.

This distinction is already visible in the runtime. Functions declared in `sys.*` accept values such as Dea `int`,
`string`, nullable wrappers, and Dea structs because their C implementations are written against `dea_rt.h` and the Dea
runtime ABI.

### Existing low-level language support

The present L1 surface already includes the mechanisms needed to write useful wrappers:

- raw pointers and nullable pointers;
- `unsafe func` and `unsafe extern func` contract markers;
- fixed-size arrays and non-owning slices;
- checked and unchecked raw-pointer access modes;
- function pointers for Dea ABI functions;
- `with` and `cleanup` for explicit resource lifetimes;
- opaque exported Dea types;
- foreign-storage registration for checked pointer access;
- separate compilation, verified interfaces, foreign objects, and common build/run linking.

This does not constitute a complete direct C ABI model. It is enough to build Dea-facing abstractions over C shims. The
current `unsafe` marker remains a contract and function-type distinction rather than a general call-site gate, so a
wrapper must still validate or document the foreign preconditions it claims to discharge.

### Current manual binding pattern

The general current pattern is:

```text
third-party C header and library
        |
        v
handwritten C shim using the actual C declarations
        |
        v
Dea-ABI functions declared through extern func
        |
        v
low-level sys.* or vendor raw module
        |
        v
ordinary safe or unsafe L1 wrapper
```

For example, a library function that returns `size_t` should not normally be declared directly as returning Dea `long`.
A shim performs the checked conversion:

```c
#include <limits.h>
#include <stddef.h>
#include <foo.h>
#include <dea_rt.h>

dea_long dea_foo_size(void *handle) {
    size_t result = foo_size(handle);

    if (result > (size_t)INT64_MAX) {
        _rt_panic("foo_size result exceeds Dea long");
    }

    return (dea_long)result;
}
```

The L1 binding remains ordinary Dea ABI:

```dea
module sys.foo;

extern func dea_foo_size(handle: void*) -> long;
```

A higher-level module can then own resource lifetime, nullability, errors, strings, and buffer extents without exposing
the foreign ABI to ordinary callers.

Direct declarations without a shim remain possible when the author has proved exact ABI identity for every parameter,
result, calling convention, layout, and target. That is a narrow manual optimization, not the general interoperability
contract.

### Link support

[Initiative 0001] implements explicit caller-asserted foreign relocatable objects through `--foreign-object` and
combines them with Dea modules in build, run, and standalone link flows. It also implements ordered external library
names, search paths, runtime search paths, and raw host-link arguments across those flows.

No additional compiler-driver work is currently needed for a supported manual binding workflow. The completed link
surface does not make bindings self-describing packages: the caller or build system still supplies the shim object and
external library options explicitly.

## Why the initiative was reconsidered

The original initiative assumed that a closed set of L1 types could cross C directly and that existing L1 scalar types
could represent ordinary C scalar types. Further analysis exposed several independent concerns that should not be
collapsed into one type whitelist.

A foreign function has at least four distinct descriptions:

1. the exact C declaration and calling convention;
2. the Dea-visible parameter and result types;
3. the conversion or adapter between those representations;
4. the access, ownership, lifetime, and escape contract around pointers and resources.

For example, C `int` is not semantically Dea `int`, even when both happen to be 32 bits on a target. C `long`, `size_t`,
and `ssize_t` are target-dependent while Dea numeric widths are fixed. A `const char *` declaration says that the callee
must not write through that pointer; it does not say whether the input is NUL-terminated, whether embedded NUL is valid,
or whether the pointer is retained after return.

This led to two broader alternatives beyond the original design: describe the C carrier explicitly in Dea, or move the
translation into generated C shims.

## Design requirements shared by all alternatives

Any resumed design should satisfy the following constraints.

### Honest C declarations

The system must preserve the actual C declaration rather than silently treating a Dea type as an equivalent C type.
Nominal C carriers such as `int`, `long`, `size_t`, and `ssize_t` remain distinct even on targets where some have equal
representations.

### Defined conversion behavior

Dea-to-C and C-to-Dea numeric adaptation must reject unrepresentable values in a defined way. An unchecked C cast that
turns a negative Dea `long` into a large `size_t` is not an acceptable language-level adapter.

### Pointer access and lifetime

Read-only access, writable access, nonescape, retention, ownership transfer, buffer extent, and termination are separate
contracts. `const` alone cannot establish a safe call.

Any foreign parameter through which C may write should at minimum require an unsafe raw boundary unless a stronger Dea
wrapper proves the writable extent and lifetime.

### Strings and views

Ordinary Dea `string` values do not use the C `char *` ABI. Cheap interior string views may also lack a NUL byte at
their logical end. A C-string adapter may therefore need to retain an existing terminated value or materialize a
temporary terminated copy. The adapter must bound the pointer lifetime and define embedded-NUL behavior.

### Compiler-family portability

Dea supports multiple C compiler families. Generated or handwritten bridge source should normally be compiled by the
same selected C compiler that compiles the Dea-generated C and matching runtime artifacts. Native objects produced by a
different compiler are only caller-asserted foreign inputs unless a tested ABI compatibility profile says otherwise.

### Bootstrap suitability

A solution should not require embedding a complete C compiler frontend into L1. A separate tool may initially be written
in Python, but its durable input, normalized binding model, and generated output should remain simple enough to
reimplement in Dea.

### Raw access and curated APIs

A general interoperability system must permit a user to bind an unanticipated library without waiting for a curated
package. Mechanical raw bindings may be unsafe. Optional curated layers can add library semantics that ordinary C
headers do not contain.

## Alternative A: direct typed C declarations

This is the design preserved in the closed [Direct C boundary plan] and the [C-string guard proposal].

The proposed language surface adds an `extern "C"` declaration envelope, a closed FFI-safe type set, extern structs and
enums, opaque C types, extern globals, optional link-name overrides, and a builtin `cstr` type.

A representative surface is conceptually:

```dea
extern "C" {
    func puts(value: cstr) -> int;

    struct CStat {
        // Declared C layout.
    }

    type CFile;
}
```

### Intended strengths

- C bindings live in ordinary L1 source.
- The analyzer can reject types outside a closed boundary.
- C names, layouts, globals, and enums become first-class compiler concepts.
- Manual binding modules need no separate generator.
- `.l1m` interfaces can carry the complete declared surface.

### Problems exposed during review

- Treating builtin L1 scalars as unwrapped C scalars is not generally honest. Dea `int` and `long` have fixed widths; C
  `int` and `long` do not.
- A flat FFI-safe type whitelist cannot describe a pair of Dea type and C carrier plus its conversion.
- C aggregate layout, enum representation, attributes, calling conventions, and typedefs introduce substantial
  target-specific compiler work.
- A builtin `cstr` mixes raw C declaration shape with Dea lifetime and materialization policy.
- The cheap-string-view direction invalidates unrestricted zero-cost `string` to `cstr` reinterpretation.
- Pointer constness does not express retention, extent, ownership, or string termination.
- Manual declarations can drift from the authoritative header without the C compiler checking the complete relation.

### Current status

This alternative is neither accepted nor rejected. The child plan is closed without implementation as a detailed record
of the original direction. Any resumed direct-declaration design must first solve target-dependent C scalar carriers and
the separation between ABI description and Dea-side adaptation.

## Alternative B: annotated Dea declarations and generated adapters

This alternative keeps ordinary Dea semantic types while attaching exact C carrier and boundary metadata to foreign
slots. The compiler emits the exact raw C declaration and an internal adapter between the C ABI and the Dea ABI.

Exploratory syntax included forms such as:

```dea
extern func puts(
    value: @cstr @noescape @const @c_char byte*
) -> @c_int int;

unsafe extern func read(
    fd: @c_int int,
    buffer: void*,
    count: @c_size_t long
) -> @c_ssize_t long;
```

The syntax is not accepted language design. It illustrates the separation:

- `int`, `long`, and pointer types remain the Dea-visible semantic types;
- `@c_int`, `@c_size_t`, and `@c_ssize_t` identify exact nominal C carriers;
- `@const` describes foreign write access;
- `@noescape` describes a lifetime promise;
- `@cstr` describes a NUL-terminated adaptation contract;
- the compiler inserts checked numeric conversions and call-scoped guards.

### Intended strengths

- One L1 declaration records both the C carrier and the Dea-facing type.
- The generated C compiler sees an exact C prototype.
- Checked conversion policy is centralized.
- The language can distinguish C `int`, C `long`, fixed-width typedefs, and size types without turning them into normal
  Dea arithmetic types.
- Imported interfaces can reproduce adapters deterministically.

### Problems and open questions

- The annotation vocabulary becomes a second C-oriented type system inside declarations.
- C carrier metadata must round-trip through `.l1m` files and participate in foreign-signature conflict checks.
- Carrier rewrites below pointers are not generally possible. A Dea `int*` cannot become a C `int*` when size or
  alignment differs without an explicit counted copy adapter.
- Buffer relationships, output parameters, callbacks, retained pointers, ownership, and errors require increasingly
  relational annotations.
- The compiler acquires target-C knowledge that could instead live in generated bridge source.
- The surface risks growing from a small FFI annotation set into a binding-description language before real programs
  establish which features are useful.

### Current status

This alternative remains a plausible direct-language design, especially if manual bindings repeatedly show that C
carrier metadata belongs beside Dea signatures. No syntax, annotation name, or semantic rule is reserved by this
initiative.

## Alternative C: generated Dea bindings and C shims

This alternative leaves the L1 language surface unchanged. A separate `dea-cbind` tool consumes selected C declarations
and emits:

```text
library_raw.l1
library_bridge.c
binding manifest or normalized binding IR
```

The generated Dea module declares Dea-ABI bridge functions. The generated C source includes the authoritative library
header and translates between Dea values and the actual C declarations. The active C compiler preprocesses the header
and compiles the bridge, so GCC, Clang, TinyCC, or another supported family remains responsible for its own target
types, attributes, calling convention, and layout.

A binding may expose two layers:

```text
mechanical raw binding
        |
        v
optional curated Dea wrapper or corrected policy
```

The raw layer should remain available when safety or idiomatic adaptation cannot be inferred. Curated wrappers add
information absent from normal C declarations, such as pointer retention, ownership transfer, buffer extents, release
functions, and error conventions.

### Possible implementation path

A first tool could be a Python program. It could:

1. invoke the selected C compiler in preprocess-only mode with the same target, include paths, definitions, and sysroot;
2. parse a deliberately limited C declaration subset or explicit copied declarations;
3. normalize selected declarations into a Dea-owned binding IR;
4. generate deterministic `.l1` and `.c` source;
5. compile the C bridge with the active Dea C compiler;
6. reject unsupported selected declarations instead of guessing.

A later implementation could be written in Dea. The permanent component need only be a tolerant C declaration parser,
not a complete C compiler. The selected C compiler remains authoritative for preprocessing and ABI interpretation.

No Clang dependency is inherent in this design. A prototype might use a pure-Python C99 parser such as `pycparser`, or a
small custom parser, provided parser-specific AST nodes do not become the binding contract.

### Intended strengths

- The L1 compiler and type grammar remain small.
- The actual C compiler validates the authoritative header and performs target-specific ABI lowering.
- C structs, macros, constants, static inline functions, and compiler attributes can remain on the C side.
- The same raw-plus-curated structure used by mature ecosystems becomes possible.
- The generator can evolve or be replaced independently of the language.
- A user can bind an unanticipated library locally without waiting for a central curated package, provided the selected
  declarations fall within the tool's supported subset or receive manual shim corrections.

### Problems and open questions

- C declaration parsing after preprocessing is still real compiler-tooling work.
- Header meaning depends on target, sysroot, feature-test macros, compiler predefined macros, and include paths.
- Generated source bundles need deterministic manifests, cache keys, and build integration.
- C headers do not encode enough semantics to infer safe strings, buffer extents, retention, ownership, or error models.
- Raw bindings can be mechanically general only by remaining unsafe and conservative.
- Some headers may not preprocess or compile under every supported compiler family.
- Cross-compiler precompiled bridge objects cannot be assumed portable; bridge source should normally be rebuilt by the
  active compiler.

### Current status

This alternative is the least invasive language design and the most natural path if repeated manual shims become the
primary burden. It is not scheduled. The present manual workflow already acts as its handwritten form and can supply
experience before any generator is designed.

## Comparison

| Question                            | Direct `extern "C"`         | Annotated declarations                  | Generated shim tool                   |
| ----------------------------------- | --------------------------- | --------------------------------------- | ------------------------------------- |
| New L1 syntax                       | Substantial                 | Moderate to substantial                 | None required                         |
| C ABI knowledge in compiler         | High                        | Medium to high                          | Low                                   |
| Target C compiler remains authority | Partly                      | Through emitted prototypes              | Yes                                   |
| Header drift detection              | Manual                      | Manual unless header checked separately | Natural when bridge includes header   |
| Raw arbitrary-library path          | Manual declarations         | Manual declarations                     | Generated or explicit declarations    |
| Curated semantic layer              | Ordinary L1 wrapper         | Annotations plus wrapper                | Policy plus wrapper                   |
| Bootstrap complexity                | Compiler and runtime        | Compiler, interfaces, and runtime       | Separate tool, later self-hostable    |
| C layout exposure to Dea            | Directly possible           | Directly possible with more metadata    | Can remain hidden behind shim         |
| String adaptation                   | Builtin `cstr` and guards   | Annotated adapter                       | Shim/runtime helper                   |
| Pointer relationship modeling       | Limited without more syntax | Annotation growth likely                | Raw unsafe layer plus curated wrapper |

No row determines the answer alone. The choice depends on what real Dea programs repeatedly need and which complexity is
worth making permanent.

## Consequences for current L1 work

### Standard library

Initiative 0003 does not block standard-library reinforcement.

- Pure algorithms and abstractions can be implemented directly in L1.
- Platform or native functionality owned by Dea can be added to the runtime C sources, declared in `sys.*` through
  existing `extern func`, and wrapped in `std.*`.
- The runtime already provides the stable Dea-ABI adaptation layer for such functions.
- String termination, pointer validation, ownership, and platform differences can remain inside owned runtime helpers.

### Third-party libraries

Manual bindings are viable now:

1. write or generate a small C shim against the real library header;
2. expose only Dea-ABI functions from that shim;
3. declare those functions through `extern func` or `unsafe extern func`;
4. place raw declarations in a low-level binding module;
5. add an ordinary L1 wrapper for ownership, errors, strings, and resource cleanup;
6. compile the shim with the same C compiler family and target used for the L1 program;
7. pass the object through `--foreign-object`;
8. pass required library names, search paths, runtime search paths, and raw linker arguments through the normal link
   CLI.

This workflow is explicit and somewhat laborious, but it does not require new language semantics.

### Initiative 0001

[Initiative 0001] is complete and closed. Its external-library linking surface remains useful even if Initiative 0003 is
postponed indefinitely. It provides the completed operational path for handwritten shims and bindings without selecting
a future language-level FFI.

### Existing FFI drafts

The closed child `extern "C"` plus `cstr` feature plan and the C-string guard proposal remain design records. They do
not describe scheduled or accepted language behavior. Diagnostic reservations and syntax choices in those documents must
be rechecked or discarded if the initiative resumes.

### C variadics and callbacks

C variadic functions, callbacks, foreign-thread entry, and other ABI-heavy features are not scheduled. A manual shim can
provide fixed-signature companion functions for specific libraries. General language or generator support should be
considered only with concrete consumers.

## Reactivation criteria

Initiative 0003 should resume only when one or more real programs provide evidence such as:

- the same C scalar conversion boilerplate recurring across independent bindings;
- repeated need for safe call-scoped string or buffer adapters outside the owned runtime;
- important libraries whose layouts or callbacks cannot be handled acceptably behind shims;
- manual binding maintenance or header drift becoming a material source of failures;
- enough raw bindings to define a stable minimum supported C declaration subset;
- performance evidence that a shim boundary is a problem rather than a theoretical concern;
- a compiler and target matrix against which one proposed design can be validated.

A reactivation plan should:

1. name the real binding cases that motivate it;
2. compare the three alternatives against those cases;
3. state which responsibilities belong to L1 syntax, the compiler, the runtime, the driver, and optional tools;
4. define the raw unsafe escape hatch before the curated safe surface;
5. preserve defined conversion and lifetime behavior;
6. avoid assuming native object compatibility across compiler families;
7. create a new or substantively revised plan rather than treating the closed child's old defaults as settled.

## Non-goals while on hold

- No `extern "C"` block syntax.
- No `@c_*` annotation syntax.
- No builtin `cstr` type.
- No extern C structs, unions, enums, typedefs, or globals.
- No C header parser in the L1 compiler.
- No `dea-cbind` implementation.
- No general C variadic or callback ABI.
- No automatic native dependency propagation from an imported L1 module.
- No backport to L0.
- No claim that arbitrary C declarations are directly ABI-compatible with existing `extern func`.

## Sequencing and dependencies

There is no scheduled phase under this initiative.

[Initiative 0001]'s external-library linking plan is complete and its link surface is available. The child feature plan
is closed without implementation and must not be revived without reactivating and revising this initiative.

## Cross-cutting concerns for a future resumption

### Stage parity

Any language or compiler surface must land first in `compiler/stage1_l0/` and define a Stage 1 and future Stage 2 parity
contract. A separate generator may have an independent bootstrap path, but generated binding artifacts must remain
usable by both stages.

### Determinism

Generated declarations, adapters, shims, manifests, and interfaces must be deterministic for identical target,
preprocessing environment, inputs, policies, and tool versions.

### Diagnostics

Diagnostics should continue to use the existing phase-oriented families unless a concrete implementation shows that a
separate topic family is necessary. Old provisional code ranges in the closed child plan are not reservations while the
initiative is on hold.

### Documentation

A resumed design must update the grammar, ABI, ownership, C backend, separate compilation, standard library, and user
binding workflow together. Until then, stable documentation should describe only the current Dea-ABI extern and manual
shim boundary.

### L0 isolation

L0 is unaffected. Its existing `extern func` primitive and runtime bindings remain unchanged.

## Glossary

- **Dea ABI extern**: an unmangled `extern func` whose parameter and result representations follow generated Dea C types
  rather than an arbitrary third-party C declaration.
- **C carrier**: the exact nominal C type used by the foreign declaration, such as C `int`, `long`, `size_t`, or
  `ssize_t`.
- **Adapter**: checked conversion, copying, guarding, ownership transfer, or other translation between a Dea value and a
  C carrier.
- **Raw binding**: a low-level, usually unsafe binding that preserves the C operation without claiming higher-level
  ownership or lifetime safety.
- **Curated binding**: a reviewed L1 layer that adds library semantics absent from the C header.
- **C shim**: C source compiled against both the real library header and the Dea runtime ABI, exposing Dea-ABI bridge
  functions.
