## Scope and findings

The eight remaining production modules contain 71 original function bodies. Review includes argument ownership,
help/version precedence, mode-scoped diagnostics, ordered link operands, command dispatch, inspection output, and
cleanup on success and failure. The inventory matches all 119 current production modules and retains the removed
`util.path` row among the 120 original entries. No modules have been added, renamed, or split.

One bounded tranche names the fields in the 31-field CLI default constructor and the four parse-result constructors,
preserving expression order and ownership transfer. It removes the unused nullable prepared-input destructor, two
uncalled C-option forwarding helpers, and obsolete not-implemented command handler after checking all repository
callers. The tested C-option merge boundary remains. Inherited Stage 1 source comments in Stage 2 entrypoints, help, and
build metadata now identify Stage 2 without changing output text.

The parser's sequential dispatch, diagnostic ordering, `ord` comparisons, native argument copying, growable owning
vectors, and build-info fallback remain intentional. No new language facility or public contract change is needed.

## Performance results

Both seven-pair series produced identical output. The initial median C-generation time changed from 24.56 to 24.50
seconds (-0.23%); the reverse-order confirmation changed from 32.03 to 33.66 seconds (+5.08%). Matched-pair median
changes were +3.71% and +1.92%, respectively; the median across all 14 matched pairs was +2.81%. Absolute times drifted
substantially for both compilers, so pooling unpaired medians across the series would not estimate throughput reliably.

The initial candidate-only 32.69-second outlier did not recur in that form: the confirmation reached 47.16 seconds for
the baseline and 45.32 for the candidate. Ranges overlap, paired differences change sign, and the large slowdown is not
consistently associated with the candidate. No material sustained regression was established; these noisy wall-clock
samples do not resolve modest throughput differences, and no speedup is claimed. The constructor C comparison
establishes unchanged generated operations/allocation behavior for the executable edits other than removal of uncalled
helpers.

Raw samples, command vectors, compiler sizes, and constructor comparison results are retained in

## Coverage and retained-helper audit

All current functions outside Phase 4 appear in the earlier review attachments except four additions from the shared
October 3 temporary-trust diagnostics fix. Those functions were reviewed here in `compiler_filesystem.l1`:
`cfs_temp_parent_field`, `cfs_temp_parent_failure_message`, `cfs_temp_parent_windows_detail`, and
`cfs_inspect_temp_parent`, together with the updated resolver and temporary-parent selection callers. Field reads use
one stable caller-owned native snapshot; temporary byte buffers and the snapshot are freed on their success/failure
paths. UID and Windows error strings preserve unsigned values without narrowing. Null diagnostics suppress reporting,
not validation. Retain these bridges and diagnostic formatters unchanged; their constants are native protocol selectors,
and ordinary stdlib filesystem calls cannot replace the trust/error snapshot contract.

The earlier module dispositions remain valid. Retained compatibility helpers fall into these concrete categories:

- Typed wrappers over erased owning containers and AST IDs (`ast`, `types`, `symbols`, semantic tables, CLI operands):
  they provide stable identities, borrowed access, and recursive/element teardown that fixed arrays and non-owning
  slices cannot supply.
- Nullable cleanup and ownership-transfer helpers (`cli_args.model`, backend state/lifetime, analysis/driver results):
  they encode conditional ownership, not obsolete L0 syntax. Blanket unsafe annotations would spread implementation
  details without establishing a better caller contract.
- Native filesystem, process, preparation, and hashing bridges: preserve host behavior, ABI, captured error evidence,
  trusted workspace checks, direct status transport, and fingerprint formats. L1 operators cannot replace these APIs.
- Numeric parsing/range helpers, checked conversion joins, and enum ordinals: preserve accepted domains, diagnostic
  behavior, and overflow boundaries. Wider types and tag-test syntax do not justify changing these contracts.
- String clones, split helpers, C-option transport, and byte escaping: callers need owned data, exact separators,
  command ordering, and stable generated-C spellings. General stdlib operations are used only where those contracts
  match. The tested CLI merge wrapper remains a deliberate boundary.
- Build metadata fallback and help/diagnostic formatting: retain the static compiler identity and exact observable
  output; distribution/provenance design remains outside this review.

The existing tests cover parsing aliases, separators, link-input validation, mode matrices, inspection and native
commands, error statuses, generated output, and ownership traces. Additional parse-result tests exercise help/version
precedence and logging/diagnostic lifetime after options are released. Additional stage-parity cases compare complete
status/stdout/stderr at those boundaries, including help after the separator and invalid link entry names. Test
adaptation is limited to these gaps; no mass rewrite of valid inherited tests is needed.

## L2 observations and follow-ups

Growing owned typed collections still require explicit erased-storage wrappers, CLI/native argument transport requires
copying into an owning vector, and enum comparisons against dynamic values use `ord`. These observations extend the
existing ledger, not the language design. No semantic defect or separate external follow-up was identified; no in-scope
work is deferred. Phase 5 remains responsible for the consolidated exhaustive gate and plan closure.
